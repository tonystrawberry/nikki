## なぜ分散コンピューティングか

コースは垂直スケーリング(1 台のマシンをアップグレードする)と水平スケーリング(マシンを増やす)の対比から始まります。

- 垂直スケーリングはすぐに天井にぶつかります。ハードウェアの限界、単一障害点、可用性の低さなど。
- 水平スケーリングなら、マシンを増やせばコンピューティングと冗長性が増えます。Spark はこれを前提に作られています。

メンタルモデルとしては、**ドライバー**がチームリーダー、**エグゼキューター**が作業者です。いくつ欲しいか、それぞれどれくらいの大きさかを宣言すると、クラスタマネージャ(YARN、スタンドアロン、または Databricks ではプラットフォーム自身)がプロビジョニングしてくれます。

## Spark のアーキテクチャ

- **ドライバー**がアプリケーションコードを保持し、論理プランを構築し、作業をスケジューリングします。
- **エグゼキューター**がデータのパーティションに対してタスクを実行します。
- ドライバーはクラスタマネージャと通信してリソースをリクエストし、そのあとエグゼキューターにタスクを送ります。
- Spark は Scala/Java で書かれていて、**PySpark** は Py4J を介して Java API の上に重ねられた Python ラッパーです。データコミュニティの多くが Python を使っているのが主な理由です。

## DataFrame と RDD

- **RDD** は元々の抽象化で、論理パーティションを持つ分散リストで、イミュータブルかつ遅延評価されます。「特徴」は、データが複数のマシンに分割されていることです。
- **DataFrame** はより高レベルな構造化 API です。内部的には最終的に RDD 操作にコンパイルされますが、その間に Catalyst オプティマイザが入ります。
- コースでは、Databricks で DataFrame を作成し、`.show()` や `.collect()` のような**アクション**がトリガーされるまでジョブが実行されないことを示しています。

## 遅延評価、トランスフォーメーション、アクション

- **トランスフォーメーション**(filter、select、groupBy、join)は DAG を構築しますが、実行はしません。
- **アクション**(show、collect、count、write)が実行をトリガーします。
- これにより、Spark はパイプライン全体を見渡してから実行するため、述語プッシュダウンや列プルーニングなどの最適化が可能になります。

## 狭いトランスフォーメーションと広いトランスフォーメーション

- **狭い(Narrow)**: 各出力パーティションが単一の入力パーティションに依存します(`filter`、`map`、`select`)。ネットワーク越しのデータ移動はありません。
- **広い(Wide)**: 出力パーティションが複数の入力パーティションに依存します(`groupBy`、`join`、`distinct`)。**シャッフル**が必要で、データがエグゼキューター間をネットワーク越しに移動します。注意しないとパフォーマンスが死ぬのはこの広いトランスフォーメーションです。

## ジョブ、ステージ、タスク

- 1 つの**アクション** = 1 つの**ジョブ**。
- ジョブはシャッフル境界(広いトランスフォーメーション)ごとに**ステージ**に分割されます。
- 各ステージは**タスク**の集まりで、パーティションごとに 1 つのタスクが対応します。
- Spark UI の DAG ビューはまさにこの階層を表しており、これをきちんと読めるかどうかが、時間がどこに消えているかを「推測する」か「知っている」かの違いになります。

## ジョイン

- **シャッフルジョイン(sort-merge)**: ジョインキーで両側がシャッフルされ、マッチする行が同じエグゼキューターに集まります。大きいテーブル同士のジョインのデフォルトです。
- **ブロードキャストジョイン**: 小さい側を全エグゼキューターに丸ごと送ります。シャッフルなし。はるかに高速ですが、ブロードキャストする側がドライバー/エグゼキューターのメモリに収まる場合に限り安全です(デフォルトの閾値は約 10 MB、調整可能)。
- Spark のオプティマイザは統計情報に基づいて自動的にブロードキャストすることもありますし、PySpark では `broadcast(df)` で強制することもできます。
- スピーカーが繰り返し強調する経験則: **シャッフルを受け入れる前に、必ずブロードキャストジョインにできないかチェックする**。

## ドライバーメモリと `.collect()`

- `.collect()` はすべてのパーティションをドライバーに引き戻します。合計サイズがドライバーの JVM ヒープを超えると、ドライバーが OOM となりアプリケーションが死にます。
- 解決策は「ドライバーを大きくする」ではほぼなく、「100 GB の DataFrame に `.collect()` を呼ばない」です。代わりに `.show(N)`、`.take(N)` を使うか、ストレージに書き出しましょう。

## 主な学び

- **遅延評価こそが本質。** まず DAG を構築し、実行前に Catalyst に最適化させる。
- **シャッフルがコスト。** すべての広いトランスフォーメーションはネットワーク操作。可能ならブロードキャストしましょう。
- **コードではなく DAG を読む。** Spark UI は*実際に*何が走ったかを教えてくれます。チューニングするのはそこです。
- **`.collect()` を盲目的に呼ばない。** 本番環境でドライバー OOM の最も一般的な原因です。
- **メモリチューニングはモデル理解の下流。** 間違った DataFrame に対する `.collect()` は、いくら `spark.driver.memory=64g` にしても救われません。
